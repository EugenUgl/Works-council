# Воркеры: жизненный цикл, очередь, контекст

> Предварительно: [`architecture.md`](architecture.md) · [`decisions.md`](decisions.md)

## Что такое воркер

Воркер — **долгоживущая дочерняя сессия**, созданная через
`ctx.subagents.startActivation`. Воркеры одного типа задачи образуют **пул**:
`read`, `web` и `write` получают по три сессии, `think` — одну
(`WORKERS_PER_TASK`, [`index.js:77`](../index.js)). Размер пула — константа
кода, а не поле конфига: строка настроек и её страница не меняются.

Создание **ленивое на двух уровнях**:

1. **Пул** появляется при первом вызове задачи: `state.workers` — пустая `Map`
   до этого, а `workerFor` вызывается только из `dispatch`.
2. **Сессия слота** появляется при первом вызове, попавшем именно в этот
   слот: записи пула — простые объекты, `startWorkerJob` вызывается из
   `runJob` лишь когда у слота `childId === undefined`.

Поэтому серийная задача навсегда остаётся на слоте 0 и не поднимает остальные
сессии; три сессии — цена параллелизма, которую платят только при
одновременных вызовах.

`workerFor` — [`index.js:1018`](../index.js) — возвращает пул
`{ task, workers[] }`; запись слота содержит:

| Поле | Смысл |
|---|---|
| `task` | `read` \| `web` \| `write` \| `think` |
| `slot` | индекс в пуле, `0…size-1`; попадает в лог замены и в статус |
| `childId` | id дочерней сессии или `undefined`, если сессии ещё/уже нет |
| `jobs` | сколько вызовов отслужила текущая сессия (**телеметрия**, не триггер) |
| `lastJobAt` | время окончания последнего вызова (**телеметрия**) |
| `environment` | снимок `environmentOf(root)` на момент последней сверки |
| `contextTokens` | последнее измерение контекста |
| `chain` | промис-цепочка: очередь вызовов **этого слота** |
| `pending` | вызовов в очереди + выполняется; по нему `pickWorker` выбирает слот |
| `observation` | активное наблюдение за текущим ходом воркера |

Все настройки задачи (`<task>Provider`, `<task>Model`,
`<task>ReasoningEffort`, `<task>MaxContextTokens`) читаются **по имени
задачи** (`routeFor(task)`, `agentOptionsFor(task, root)`), поэтому пул
получает их целиком, без отдельной «передачи настроек» между воркерами.

## Главное правило: история воркера важнее замены

Воркер — это накопленная история чтений/записей, и именно она делает
последующие вызовы дешёвыми. Поэтому **заменяет воркера ровно одна причина:
израсходованный контекстный лимит** (`<task>MaxContextTokens`).

Всё остальное сессию **не** заменяет:

| Событие | Что происходит |
|---|---|
| Простой (долгий ход основного агента) | ничего; сессия сохраняется |
| Счётчик вызовов | ничего; `maxJobsPerWorker`/`workerIdleMs` ещё читаются из конфига, но **жизненным циклом не управляют** (см. «Долг» ниже) |
| Смена режима песочницы или `cwd` | `refreshWorkerEnvironment` **перепривязывает** воркера, не пересоздавая |
| Ошибка одного вызова (ошибка инструмента, отказ верификации, ответ без вызова инструмента) | `failures += 1`, `lastError`, `warn`; сессия остаётся, следующий вызов повторяется в ней |
| Ошибка компакции | `compactionFailures += 1`, сессия остаётся (кроме отмены) |
| Ход не дошёл до `turn/end` | `failures += 1`, `warn` с пометкой «unsettled turn»; **сессия остаётся** |
| Выключение задачи (`*Enabled: false`) | `retireIdleWorker` только логирует; воркер остаётся резидентным и возобновляется при включении |
| Ребёнок пропал из `ctx.agents` | `warn` и запись сохраняется как есть; новой сессии это не запускает |

### Ход, который не завершился

Раньше такой ход считался основанием для замены. Теперь это
**наблюдение**, а не решение: `runJob` по-прежнему отслеживает `turnSettled`
(его возвращают `startWorkerJob`/`continueWorkerJob`), но в `catch` только
пишет `warn` и увеличивает `failures`. Причина: пользовательское правило —
воркера заменяет только контекстный лимит; если застрявший ход действительно
мешает, это упирается в лимит и приводит к замене уже по нему.

Чтобы зависший ход не подвешивал вызов навсегда, ожидание ответа в
`continueWorkerJob` обёрнуто в `withTimeout(answer, signal)`: таймер
observation снимается в `finally` раньше, чем следующий вызов успел бы на него
положиться.

Зафиксировано в [`test/worker-lifetime.test.mjs`](../test/worker-lifetime.test.mjs)
(кейсы 6 и 8) — см. также
[`decisions.md`](decisions.md#d15-воркера-заменяет-лимит-контекста-а-не-ошибка).

## Очередь и выбор слота

`dispatch` — [`index.js:1428`](../index.js):

```js
const worker = pickWorker(workerFor(state, task));
worker.pending += 1;
const run = worker.chain.then(() => runJob(...));
worker.chain = run.then(() => {}, () => {});   // ошибка не рвёт цепочку
const settle = () => { worker.pending -= 1; };
run.then(settle, settle);
return run;
```

- **У каждого слота своя цепочка**: одна сессия по-прежнему не ведёт два хода
  одновременно.
- **`pickWorker` выбирает слот с наименьшим `pending`** — [`index.js:1065`](../index.js).
  Это и есть параллелизм пула: без выбора все вызовы вставали бы в одну
  цепочку, и три сессии ничего бы не изменили.
- **Ничья уходит младшему слоту**, поэтому серийная задача копит историю на
  слоте 0, а не размазывает её по трём.
- **`write`/`edit` выбираются иначе — по `file_path`** (`fileWorker`,
  [`index.js:1093`](../index.js)). Один файл всегда попадает в один слот, то
  есть в одну цепочку. Это не оптимизация, а условие корректности: снимок
  `before` для проверки записи берётся **внутри** `runJob`, поэтому два
  параллельных изменения одного файла предсказывали бы от одного и того же
  содержимого, и автоисправление второго перезаписало бы файл по устаревшему
  предсказанию — молча потеряв первую правку. Разные файлы по-прежнему
  расходятся по слотам и идут параллельно; коллизия хэша стоит только
  параллелизма, но не порядка.
- **Сверх пула вызовы ждут**, а не открывают четвёртую сессию: освободившийся
  слот получает следующего из очереди (продолжение той же сессии).
- **Разные типы задач независимы** — у каждого свой пул.
- Падение одного вызова не блокирует следующие: цепочка продолжается
  через `.then(ok, err)`.

Проверяется `test/pool.test.mjs`: три параллельных `read` поднимают три
сессии, четвёртый вызов ждёт и продолжает освободившийся слот, восемь
последовательных `read` остаются на слоте 0, два `write` одного файла идут
строго по очереди, а разных — параллельно.

### Пул и история

Пул распределяет вызовы по трём сессиям, поэтому история одного слота растёт
примерно в три раза медленнее, чем при одном воркере. Это осознанная цена
параллелизма: `<task>MaxContextTokens` срабатывает реже по числу вызовов, но
каждый слот компактится независимо. `delegate_inspect` идёт в пул `read`, то
есть делит очередь с обычными `read`.

## Путь вызова

`runJob` — [`index.js:1263`](../index.js):

1. `refreshWorkerEnvironment(state, worker)` — если окружение изменилось,
   `ctx.get('workingDirectory').set(child, cwd)` и `info`-лог; сессия та же.
2. `await compactWorkerIfOverLimit(state, worker, exec.signal)` — единственная
   точка, где воркер может быть заменён.
3. Промпт: `persona(definition)` + `taskMessage(...)` с аргументами в JSON.
4. `startWorkerJob` (если `childId === undefined`) или `continueWorkerJob`;
   оба возвращают `turnSettled`, который `catch` только логирует.
5. `worker.jobs += 1`, `lastJobAt = Date.now()` — только телеметрия слота.
6. Для `capture: 'answer'` — проверка `usedTool`.
7. `settleVerification`, затем `capResult`. Дайджест (`budgetStrategy: 'summary'`)
   выполняется **в том же слоте**, что и вызов: промпт ссылается на «твой
   предыдущий вызов», которого в чужой сессии не было.
8. `catch`: `failures += 1`, `lastError`, `warn`, `throw`; **рецикла нет** —
   `turnSettled` лишь попадает в сообщение лога.

### `startWorkerJob` — [`index.js:905`](../index.js)

- `ctx.subagents.startActivation({ provider, delivery: 'caller', request: { parent, prompt, cwd, agentOptions } })`.
- `workersByChild.set(childId, { state, worker })` — чтобы наблюдатель ловил события.
- `worker.environment = environmentOf(root)` — фиксируем окружение запуска.
- `await withTimeout(activation.result, signal)`; при успехе `turnSettled = true`.
- Возвращает `{ text, failed, usedTool, turnSettled }`.
- `finally`: снять наблюдение и `activation.dispose()`.

`dispose()` закрывает receipt и локальный handle, но **не** отменяет дочерний
агент — поэтому сессия остаётся в `ctx.agents` и переиспользуется (контракт — в
[`test/probe.test.mjs`](../test/probe.test.mjs)).

### `continueWorkerJob` — [`index.js:944`](../index.js)

- Свой `observation`/`job` с `finish`/`abort` и таймером; на таймаут —
  `interruptWorker`.
- `ctx.subagents.sendMessage(root, childId, [...], { signal })` → ждём `turn/end`;
  получение `turn/end` ставит `job.turnSettled = true`.
- `signal.addEventListener('abort', onAbort, { once: true })`.
- Возвращает `{ text, failed, usedTool, turnSettled }`.

### `recycleChild` — [`index.js:833`](../index.js)

Сбрасывает `childId`, `jobs`, `environment`, `observation` **одного слота**,
увеличивает `state.recycled`, учитывает причину в `state.recycleReasons`,
пишет `info`-лог с номером слота, снимает запись из `workersByChild` и вызывает
`ctx.subagents.drainChildren`. Слот становится «пустым»; **очередь слота при
этом переживает рецикл** — вызовы, ждавшие в его цепочке, не теряются.
Остальные слоты пула замену не замечают. Вызывается из
`compactWorkerIfOverLimit`
(единственная штатная замена) и `recycleAll` (закрытие агента или выгрузка
плагина).

## Журнал замен

Каждая замена проходит через `recycleChild(state, worker, reason)`. Причина
пишется в `info`-лог и учитывается в телеметрии:

```
delegate-io: replacing the <task> worker <childId> (<reason>)
```

| `reason` | Когда |
|---|---|
| `context limit spent (<after> >= <limit>)` | компакция не уложила историю в лимит — **единственная** штатная причина |
| `root agent released` | агент закрыт (`recycleAll`) или плагин выгружен |
| `unspecified` | значение по умолчанию — если увидели его в логе, новый путь забыл причину |

`delegate_io_status` отдаёт `recycled` (всего замен) и `recycleReasons`
(разбивка по причинам). **Незалогированная замена — баг:** именно поэтому
молчаливые замены раньше выглядели как «поток новых воркеров».

## Окружение воркера

`environmentOf(root)` — [`index.js:634`](../index.js) — строка
`"<sandboxPolicy.mode>\0<cwd>"`.

Воркер фиксировал разрешения и рабочий каталог родителя при создании. Теперь
рассинхронизация **не** пересоздаёт сессию: `refreshWorkerEnvironment`
([`index.js:1168`](../index.js)) перепривязывает воркера к текущему `cwd`
через сервис `workingDirectory` и логирует это. Если перепривязка не удалась —
`warn`, но сессия сохраняется.

## Лимит контекста и компакция

`compactWorkerIfOverLimit` — [`index.js:1201`](../index.js) — **единственный**
триггер замены:

1. `limit = contextLimitOf(task)`; `0` — лимита нет, выходим.
2. `liveWorkerAgent(childId)` — найти живой `Agent`. Не найден → `warn`, запись
   сохраняется, новой сессии не запускается.
3. `before = contextTokensOf(child.session)`; `before < limit` — выходим.
4. `ctx.compaction.compactNow(child, signal)`:
   - бэкенда нет → `info`-лог, **сессия сохраняется**;
   - ошибка → `warn`, `compactionFailures += 1`, **сессия сохраняется**
     (кроме `signal.aborted`, который пробрасывается).
5. После компакции: `after >= limit` → рецикл. **Лимит жёсткий** — историю,
   которая не уменьшается, можно уложить только новой сессией.

Итог: лимит контролирует размер, но не наказывает за временный сбой
компактора.

### Почему `surfaceTokens`

`contextTokensOf` — [`index.js:1142`](../index.js) — читает
`tokenMeter.measure(session).surfaceTokens`, **не** `contextPressure()`.
Обоснование — [`decisions.md`](decisions.md#d3-почему-surfacetokens-а-не-contextpressure).
Коротко: `pressureTokens = input + cacheRead + cacheWrite`, и кэшированный
воркер выглядел в разы больше себя, из-за чего пересоздавался почти каждый вызов.

### Что лимит **не** покрывает

Маршрутизированные инструменты и системный промпт не входят в `surfaceTokens`,
поэтому лимит консервативен. Если нужна точность — добавлять компоненты
сверху, а не менять метрику.

## `liveWorkerAgent` — [`index.js:1111`](../index.js)

Поиск живой сессии двумя путями: `ctx.agents.get(childId)`, затем
`ctx.agents.list().find(...)`. Ошибка списка логируется и даёт `undefined`.

## Отключение задачи на лету

`retireIdleWorker(state, task)` — [`index.js:868`](../index.js). Вызывается из
клона при `${task}Enabled === false`. Воркер **не** освобождается: сервис
только пишет `info`-лог, а резидентная сессия дожидается повторного включения
задачи (и тогда обслуживает вызов с сохранённой историей) или своего лимита
контекста.

## Отмена и таймауты

| Источник | Что происходит |
|---|---|
| `requestTimeoutMs` (15 мин) | `withTimeout`/таймер observation → ошибка → `interruptWorker` |
| `signal.aborted` | «the delegated call was cancelled», `onAbort` прерывает воркер |
| Ошибка внутри `runJob` | `failures += 1`, `warn`, `throw`; сессия сохраняется; клон уводит в fallback |
| Ход воркера не завершился | `failures += 1`, `warn` с пометкой «unsettled turn»; сессия остаётся |

`continueWorkerJob` ждёт ответ через `withTimeout(answer, signal)`: воркер,
принявший сообщение и не закрывший ход, иначе подвесил бы вызов навсегда —
таймер observation снимается в `finally` раньше, чем следующий вызов успел бы
на него положиться. Флаг `turnSettled` — единственный признак непригодной
сессии; `worker.observation === undefined` таким признаком не был, потому что
`finally` очищает его и при обычных ошибках.

Тест таймаута держит `requestTimeoutMs` **в конфиге плагина** (не в опциях
харнесса) и ставит 50 мс: с дефолтными 15 минутами кейс вешал бы весь набор.

## Технический долг этой области

`maxJobsPerWorker` и `workerIdleMs` остались в `Config`, в `cordis.patch.yml`,
в форме настроек и в аксессорах, но **больше не влияют на жизненный цикл**.
Это расхождение «настройка обещает — код не делает»: либо вернуть поведение,
либо пометить поля как устаревшие и убрать из формы. См.
[`development.md`](development.md#технический-долг).

## На что легко сломать

- **Добавили `await` до цепочки `worker.chain`** — вызовы полезут в одну
  сессию параллельно.
- **Вернули `observation` не в `finally`** — события следующего хода попадут в
  предыдущий.
- **Снова начали рециклировать по простою/счётчику/окружению/ошибке** —
  вернётся «поток воркеров»; маркер —
  `test/worker-lifetime.test.mjs`.
- **Убрали рецикл при `after >= limit`** — лимит перестал быть лимитом.
- **Поменяли `contextTokensOf`** — см. D3.

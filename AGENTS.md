# Правила работы с этим проектом

> Эти правила действуют для любого агента (и человека), который меняет файлы
> в `dsh-plugin-delegate-io`. Они дублируются в `CLAUDE.md` на случай, если
> среда читает только это имя.

## Правило №1 — сначала документация, потом код

**Перед любой работой с файлами проекта прочитай документацию.** Не полагайся
на память, на предыдущее чтение файла в этой сессии или на догадки по названиям
символов.

Порядок обязателен:

1. `README.md` — что это за проект, как запускать тесты, где лежит что.
2. `docs/README.md` — карта документации, выбери нужные страницы.
3. Профильная страница (по типу задачи — см. таблицу ниже).
4. Только после этого открывай код и вноси изменения.

| Что собираешься менять | Обязательно прочитать сначала |
|---|---|
| Делегирование `read`/`web`/`write`/`edit`, клоны инструментов | `docs/architecture.md` |
| Жизненный цикл воркера, очередь, рецикл, контекст | `docs/workers.md` |
| Обрезку/спилл/дайджест результата | `docs/results-and-budget.md` |
| Верификацию `write`/`edit` | `docs/verification.md` |
| `delegate_think`, `delegate_inspect`, `delegate_io_status` | `docs/tools.md` |
| Любое поле конфига, `cordis.patch.yml`, страницу настроек | `docs/configuration.md` |
| `client.js` (форма, слоты, сохранение) | `docs/configuration.md` + `docs/architecture.md` |
| Тесты, регрессии, «почему так сделано» | `docs/testing.md` + `docs/decisions.md` |
| Выпуск новой версии | `docs/development.md` |

Если документация расходится с кодом — **сначала исправь документацию**
(или отметь расхождение), и только потом меняй код. Документация — источник
истины о намерениях, код — источник истины о фактах; расхождение — это баг.

## Правило №2 — уважай инварианты

Перед правкой проверь, что не ломаешь ни один из них
(`docs/architecture.md` → «Инварианты»):

- каждое поле `Config` объявлено `.volatile()`;
- клон инструмента регистрируется независимо от `*Enabled`;
- `*Enabled` читается на каждом вызове, а не при регистрации;
- при отказе воркера работает `fallbackToDirect`;
- ошибка верификации записи (`delegateIoVerification`) **не** уходит в fallback;
- фильтр `agent/pre-step` никогда не отказывает в шаге — он может вернуть
  пустую `enter`-пачку;
- отчёт воркера без единого вызова инструмента считается невалидным.

## Правило №3 — каждая правка сопровождается тестом

Проект держит тесты как **регрессионные маркеры**: каждый хитрый баг оставлен
в коде и в тесте комментарием, объясняющим, почему так, а не иначе.

- Новое поведение → новый тест в `test/`.
- Исправленный баг → тест, который падает на старом коде.
- `npm test` должен проходить полностью; `test/probe.test.mjs` — намеренно
  зонд, читай его перед изменением логики `ctx.agents`/`dispose()`.

## Правило №4 — стиль кода

- ESM, табы, одинарные кавычки, точки с запятой — как в существующих файлах.
- Каждая нетривиальная функция получает JSDoc с `@param`/`@returns` и, если
  причина неочевидна, абзацем «почему» в начале.
- Комментарии объясняют **причину**, а не пересказывают код.
- Не рефактори и не переформатируй файлы попутно с задачей: диф должен быть
  обозримым (`docs/development.md` — известные косметические долги).

## Правило №5 — ничего не ломать молча

- Никаких «немых» падений: если воркер или спилл недоступен, пиши
  `ctx.logger.warn` и деградируй явно (отдай результат целиком / выполни
  инструмент напрямую), как это уже сделано в `capResult` и `saveSpill`.
- Любой новый отказ (throw) должен нести контекст: что делегировалось, что
  ожидалось, что получилось.

## Правило №6 — не трогать чужие файлы

- Профиль DSH (`~/.dsh/profiles/desktop`) и `node_modules` — только чтение.
- `cordis.patch.yml` этого пакета — часть поставки: поля в строке должны
  соответствовать схеме `Config` один-в-один.
- Обновление зависимостей — отдельная задача, не «попутная».

## Правило №7 — правка не закрыта, пока документация не актуализирована

**Любая правка кода автоматически влечёт правку документации — в той же
задаче.** Это не «хорошо бы потом»: задача считается незавершённой, пока
документация не описывает то, что теперь делает код.

Порядок — **после** изменения кода и **до** отчёта о завершении:

1. **Сверь утверждения.** Каждая страница, описывающая затронутое поведение,
   должна совпадать с кодом фактически, а не по памяти.
2. **Обнови содержимое.** Что изменилось в поведении — то и в тексте: таблицы
   «что происходит при…», шаги алгоритма, причины, значения по умолчанию.
3. **Обнови ссылки `файл:строка`.** Вставка нескольких строк сдвигает все
   номера ниже. Пересчитай затронутые ссылки (`Select-String -Pattern
   'index\.js:'` по странице) и сверь с реальными объявлениями функций.
4. **Допиши журнал.** Архитектурная правка → новая или исправленная запись в
   `docs/decisions.md` (D-номер, «почему», «если откатить»). Новая регрессия →
   строка в `docs/testing.md`. Новое поле `Config` → `docs/configuration.md`.
5. **Проверь, что не осталось устаревшего.** Поищи по `docs/` имена удалённых
   функций, значений и причин, которых больше нет в коде.

| Куда смотреть | Когда обязательно |
|---|---|
| `docs/workers.md` | менялся жизненный цикл, рецикл, очередь, лимит контекста |
| `docs/architecture.md` → «Инварианты» | менялось правило, которое нельзя нарушать |
| `docs/decisions.md` | принято архитектурное решение или отменено прежнее |
| `docs/testing.md` | добавлен, изменён или удалён тест |
| `docs/configuration.md`, `cordis.patch.yml`, `client.js` | менялся `Config` или форма настроек |
| `docs/tools.md` | менялся контракт или вывод глобального инструмента |
| `docs/README.md` | появилась новая страница документации |

**Красный флаг.** Если правка изменила поведение, а в документации не
изменилось ни строки — правило нарушено. «Документацию сделаю отдельной
задачей» допустимо, только если пользователь прямо об этом попросил, и тогда
это фиксируется как долг в `docs/development.md`.

## Правило №8 — утверждение о состоянии системы — только после проверки

**«Этого нет» — это факт, а не ощущение.** Перед тем как заявить, что файла,
поля, инструмента или сервиса не существует, проверь источник. Непроверенное
утверждение называется гипотезой и так и формулируется.

Почему это правило существует: в одной сессии агент дважды объявил
несуществующим реально существующее — сначала набор страниц `docs/*.md`
(спасло то, что утверждение проверили), затем инструмент `delegate_think`,
который присутствовал в **каждом** заголовке запроса. Второй раз это стоило
часа работы без эскалации: агент не вызвал мыслителя, потому что решил, что
инструмента у него нет.

**Что проверять и чем:**

| Утверждение | Где проверять |
|---|---|
| «инструмент недоступен» | `delegate_io_status` → `tools`; последний `request/header` журнала сессии |
| «поля конфига нет» | `Config` в `index.js`; профиль `~/.dsh/profiles/desktop/cordis.patch.yml` |
| «код не применился» | `StartTime` процесса DSH против `LastWriteTime` файла |
| «файла/страницы нет» | `glob`/`Get-ChildItem` по каталогу, а не по памяти |
| «поведение работает так» | строка кода или вывод теста, а не документация |

**Красный флаг.** В отчёте появляется «нет», «отсутствует», «не
зарегистрирован» без команды или ссылки, которая это подтверждает.

## Быстрый старт для агента

```powershell
# 1. Прочитать документацию (правило №1)
Get-Content README.md, docs/README.md

# 2. Найти нужную страницу в таблице выше и прочитать её.

# 3. Только теперь — код.
```

Тесты (Node берётся из runtime DSH, если `node` нет в `PATH`):

```powershell
$node = 'D:\Soft\DeepSeek\resources\runtime\primary-runtime\dependencies\node\bin\node.exe'
& $node test/schema.test.mjs
# или все подряд — та же цепочка, что в package.json → scripts.test
```
